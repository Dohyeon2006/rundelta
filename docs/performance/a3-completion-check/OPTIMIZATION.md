## 行为与实现

`capture::record` 只替换根/退出/缺失集合的搜索；`Completion::from_events` 一次遍历 events，使用 `BTreeMap<&str, Option<&Event>>`。每个 event.pid 和 Some(child_pid) 建立条目，exit 更新最后退出引用，第一个成功 exec 选择根。遍历后查根退出，并按字符串字典序生成缺失 PID 列表。子 PID 仅被提及也必须有退出；后来的 fork 提及不会抹去早先 exit。

结构复杂度从最坏 O((E+S)E) 降为 O((E+S) log P + P)，额外状态 O(P)，其中 S 是非空 child_pid 数。借用字符串和事件，不复制完整事件或每次 clone PID。单遍指 events 遍历一次，最后仍遍历 PID 表生成稳定告警，不能宣称完全不扫描任何集合。字符串比较成本另计。

根退出原文/最后 exit、未知信号、128+signal 与真实信号、采集器失败、缺失子进程、解析警告、CWD 不确定及完整性分级均由原分支处理。采集器启动失败路径也会执行聚合，但不发布额外缺失警告，原失败语义保留。没有更改信号转发、pidfd、PDEATHSIG、kill-on-exit、等待/锁、最终存储校验、schema、v1/v2/v3 策略、排序或冻结输入。

## 结论与限制

**实测确认 32,000 事件明显改善。** dev 检查中位数由 6,173–6,366 ms 降为 1.579–4.626 ms，原生 record 从 6.47–6.57 s 降到 0.514–0.564 s。release 检查由 898–962 ms 降到 0.458–0.686 ms，record 从 1.02–1.17 s 降到约 0.114 s。所有规模均改善；完成检查已不再主导这组输入的耗时。更小的区间已明显受 GDB 开销影响，不据此拟合精确常数或跨 PID 单调性。

**结构推断**：每个事件有一次 PID 查找及至多一次 child_pid 查找，消除了同一 PID 出现次数乘整表搜索。实测不代替该证明；没有声称所有输入时间都精确线性。**内存取舍**：以前完整记录的缺失集合为空，新实现仍持有所有 P 个 PID 的 O(P) 状态；避免 E 次字符串分配，但不能保证总内存总是减少。32k 检查高水位 dev 约 21 MB、release 约 19 MB，前后范围重叠，不能从 RSS 声称显著节省。保存阶段仍有完整序列化/读回/反序列化开销，未优化。

环境：AMD Ryzen 7 9700X，16 逻辑 CPU，affinity 0–15；Linux 7.2.5-200.fc44.x86_64；rustc 1.98.1、Python 3.14.7、GDB 17.2-2.fc44；实际版本字符串见各 JSON。临时记录位于本机 tmpfs，未绑核、锁频或隔离系统负载。dev opt-level=0；release opt-level=3/debug=2。壁钟含 GDB 停止/恢复，未扣除固定开销。外部 native wall 使用原脚本 subprocess 超时等待，有轮询量化/上浮；GNU time 用户/系统/elapsed 也保留，不能直接相减推导阶段耗时。

未测：P>128、百万事件、真实内核同时创建大量进程、不同事件分布的性能矩阵、其他 Linux ABI、冷盘/NFS、OOM/分配失败。实际五案例 traces 的重放等价性不是真实目标的性能基准。pid 复用/复杂 namespace/脱离追踪等生命周期边界未扩大。release 机器码查找依赖有符号的当前编译器产物；其他编译器若改变代码布局，脚本拒绝测量，需要重新核实边界。

## 审计契约修正与最终收尾
