# 采集前测量方案

只观察原产品代码。完成检查在 capture::record 内部，不在 store::load 内；不能用读取耗时代替完成检查，不能把重写的循环称作产品性能。

主实验固定当前 dev 二进制（默认 opt-level=0），GDB 在 capture.rs 198 与 209 行前后单次断点观察 missing_exits 的原始机器码；258 行取完成保存后的进程 VmHWM。断点时间包含恢复/再次停止的小量开销，作为区间 wall-time 估计，不是纯 CPU 指令时间。记录进程峰值近似（/proc VmHWM），不把 GDB 自身内存当目标内存。脚本绑定源码摘要及行号，源码变化须重新审查边界。

输入为显式标记的合成追踪：一个 root exec、P-1 个 fork、均匀分布的绝对路径 open、最后 P 个退出，根最后退出。总事件 E 固定，open 数 E-2P；PID 固定长度。不是实际程序执行记录，不声称真实采集性能。合成后端只向 -o 写 fixture，真正的 RunDelta 仍执行 trace 读取、解析、完成检查、保存和最终校验。随后使用真正 show/list/diff 路径验证保存结果；show 耗时包含读取、摘要校验、反序列化、JSON 编码与向 /dev/null 输出，不称为单独的加载耗时。

预登记主矩阵 E=2,000/8,000/32,000 与 P=1/16/128 的笛卡尔积（九组），每组 3 次；E、P 独立控制，不用一条混合规模曲线代替。每次使用独立存储根，避免目录扫描规模混杂。随机顺序固定 seed=20260920；每组额外一次非计入主统计的端到端 warmup/校验。再对相同矩阵做无 GDB 的 record 端到端及 show 读取路径各 3 次，用 GNU time 取得进程时间与 max RSS。

报告 min/median/max、样本标准差、全部脱敏样本，失败样本保留且不能换规模抹去。主实验不给预期耗时或改善倍数。先做 E=2,000/P=1 的可行性试运行（不计主样本）。若调试器断点无法可靠命中，明确记录受限，不以端到端时间伪装完成区间时间。

模型单独计算每个 PID 出现次数和其 exit 位置的加权和，作为代码层预测的 any() 谓词访问次数，不是计时循环。候选单遍方案只写设计，绝不运行候选实现来宣称加速。
