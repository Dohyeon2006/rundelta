## 测量是什么，不是什么

完成检查在 `capture::record`，不在读取旧记录的 `store::load`。我们没有重写循环来计时，也没有把 show 的耗时冒充完成检查。

- 现有 RunDelta 二进制不变。GDB 用三个单次观察断点：capture.rs:198 开始收集 missing_exits，209 在收集结束后，258 在保存完成后。27 次测量均验证各断点恰命中一次，所在 frame 都是 `rundelta::capture::record`，目标退出码 0。
- 主完成区间计时实际执行原产品的迭代器/字符串复制/any 搜索/缺失 PID 集合构造，不包括前面的解析、后面的警告拼接和 store::finish。wall-time 包含调试器停止/恢复及调度影响，不是硬件 CPU 计数。
- 通过 `RUNDELTA_STRACE` 指定明确标注的**合成追踪生产器**，它只写入 fixture，从不执行传入目标。P 指记录里的唯一 PID 数，不是本机实际 fork 出 P 个目标。记录的 backend 字段明确写明 synthetic/not strace；不能把这些数据作为真实程序运行的证据。
- 真正的产品仍读 trace、解析、执行完成检查、写 events/metadata/finalized。每个 warmup、GDB 和 native record 都经过产品 `list --json` 的读取与摘要/计数校验以及 `diff synthetic synthetic --json`，断言存储 verified、采集 complete、自比较无差异且退出 0。没有使用 Python 自行读 JSON/算摘要来代替产品校验。主测量之后又对九组 warmup 记录使用真实 show 读取全部事件，核对实际 E/P/退出 PID 数和计数模型；结果见 [RECORD_CHECKS.json](RECORD_CHECKS.json)，不计入耗时样本。
- 无 GDB 的 record 与 show 分开计时。show 使用同一个二进制的完整读取/校验路径，包含 JSON 序列化与 `/dev/null` 输出；数据已被前面的校验读过，属于**热读取**，不是冷盘或纯 load 基准。

[完整统计表](MEASUREMENTS.md) 包含 min/median/max、样本标准差与目标进程 VmHWM；[RESULTS.json](RESULTS.json) 保留每次计时、所有内存指标及其完整统计。未隐藏 8,000/P=128 组的较大波动（295.204–353.509 ms，样本标准差 33.203 ms）。

P=1 时，事件数增加 16 倍，完成检查中位数增加约 **341 倍**。代码预测的 any 谓词访问从 400 万增加到 10.24 亿（256 倍）。实测增长与平方级重复搜索相符，但不把壁钟增长拟合值等同于精确算法次数，也不臆测缓存/调频等差异的具体成因。

32,000 事件时，检查结束处的目标进程 VmHWM 中位数约 21,296–21,420 KiB，最终保存后约 50,864–51,124 KiB。后者包括序列化、读回和重新解码，不是完成检查单独分配的内存。内存没有呈现与检查时间同样的平方增长；本轮也未测得内存泄漏。

附加五次最小工作量校准（E=2/P=1、原代码仅四次模型谓词访问）区间为 0.058–0.105 ms，中位数 0.069 ms，见 [CALIBRATION.json](CALIBRATION.json)。这有助于排除“18 ms 完全来自两个断点固定开销”的解释；它不是纯调试器开销测量，也没有从主结果中扣除。

### 环境与误差边界

- AMD Ryzen 7 9700X，16 逻辑 CPU，未固定单核；本次可用 affinity 0–15；performance governor，未锁定频率或隔离其他负载。
- Linux 7.2.5-200.fc44.x86_64，约 31,981,628 KiB 物理内存；临时测量目录位于 tmpfs，不能外推真实磁盘 fsync 延迟。
- Rust 1.98.1、Python 3.14.7、GDB 17.2-2.fc44、GNU time 1.9；ptrace_scope=0。
- 测现有 `target/debug/rundelta`，按其既有 cargo dev 构建（opt-level=0、调试信息）解释结果。二进制和 capture 源码 SHA-256 存于 RESULTS；未新建 release 构建，脚本不能自动推断任意传入二进制的优化级别，复现必须使用指定 dev 条件。
- native record 包含合成后端的 Python 启动/拷贝、产品解析、完成检查、持久化；不代表真实 strace 的开销。
- 外部 wall-time 使用带 timeout 的 Python subprocess 等待，存在轮询等待的量化/额外延迟；GNU time 的 elapsed/user/sys 另存每个样本，精度为 0.01 s。尤其不能用小规模的 record/show 壁钟相减推算阶段时间。完成检查的 GDB 区间不使用这一 subprocess 等待时钟。
- VmHWM 来自目标进程 `/proc/<pid>/status`；GNU time 的 max RSS 也保留，但 record 的值可能受被等待子进程影响，不混作扫描专属峰值。每组只有三次，提供范围与标准差，不声称高置信度总体分布。

## 代码模型与候选设计

完整调用链、扫描范围、变量定义、计数公式与候选状态见 [DESIGN.md](DESIGN.md)。关键结论：原代码对 E 个事件和 S 个 child_pid 产生 Q=E+S 次查询，每次都从事件开头搜索退出；最终的 BTreeSet 只去重缺失结果。尾部退出使绝大多数搜索接近 E，形成 O(QE) 的最坏路径。

固定 E 时，增加 P 同时减少用于填充的 open 数（E−2P），改变了事件类型占比，因此不能把这些小幅耗时差全部归给 P。本输入的精确计数模型已包括该变化。在 E=32,000/P=128 时模型约 10.26032 亿次，比 P=1 仅增加约 0.2%，与“固定 E 没有数量级 PID 效应”相容。

候选只遍历一次，按 PID 保留出现状态、是否见 exit、最后 exit 索引，并独立保留第一个成功 exec 的根 PID。采用有序表可将这部分降为 O(E log P + P)、状态 O(P)，保持缺失列表的字典序和全部异常语义。预计消除大量重复比较，但解析、证据、存储校验和生命周期不得删减；端到端收益不会等于谓词次数的理论比例。

## 复现命令

前提：Linux、Python、GDB Python 支持、GNU time、允许启动被调试进程；二进制须与基线源码匹配，并带 dev 调试信息。测量脚本检查 198/209/258 行锚点；源码或工具链变化后应重新核对断点，不自动寻找“看起来相似”的位置。

```bash
# 使用已构建的 dev 二进制；本轮没有重建或修改产品。
python3 -B docs/performance/a3-completion-check/measure.py \
  --binary "$PWD/target/debug/rundelta" --repeats 3

# 可选的最小工作量校准；只输出脱敏数值 JSON。
python3 -B docs/performance/a3-completion-check/calibrate.py \
  --binary "$PWD/target/debug/rundelta"

# 可选：对 measure.py 打印的私有工作目录再次走实际产品读取路径。
python3 -B docs/performance/a3-completion-check/verify_records.py "$ARTIFACTS" \
  --binary "$PWD/target/debug/rundelta"

# 对已公开的测量摘要重新计算统计并核对测量脚本/预登记摘要。
python3 -B docs/performance/a3-completion-check/verify.py
```

测量顺序、fixture 构造、warmup 排除策略事先记录在 [PLAN.md](PLAN.md)，其摘要已在结果中核对。measure.py 每次新建仓库外临时目录，打印 PRIVATE_ARTIFACTS 和 RESULT_JSON；不读取或修改旧运行记录，不将完整追踪或记录加入仓库。若需要重新构建，使用独立仓库外 target-dir 和相同 dev 配置，并报告新的 binary SHA；不要把构建产物复制到本目录。

公开目录仅包含本报告、计划/设计、复算脚本和脱敏数值。私有临时目录中的 synthetic trace、metadata、events、GDB 日志等不是公开附件；复算统计无需它们。为严谨复验完整执行路径，应重新运行 measure.py，而不是把数值 JSON 当成原始记录。

## 结论的证据等级

- **已实测**：九组输入均通过实际产品采集后处理、保存、读取校验和自比较；本 dev 构建在 8,000 事件已达约三分之一秒，在 32,000 事件达约六秒的完成检查；固定 E 的 P 效应未见单调恶化；统计/指纹复算通过。
- **代码结构推断**：any 的加权访问公式与 O(QE) 最坏复杂度；候选单遍表的复杂度；读取路径不重复执行 capture 的 missing_exits。计数公式未用硬件 profiler 逐次验证。
- **未测量**：release/其他 CPU、冷盘/NFS、真实项目事件分布、退出分散或大量缺失退出时的性能、真正的大量 OS 子进程、候选实现的时间/RSS、可信加速倍数。语义风险须由设计列出的新回归覆盖。

**值得进入实现阶段**：问题已在当前使用的 dev 二进制和中等合成规模上量化，候选改动可限定为完成状态聚合。最重要风险是误改根进程选择、最后 exit/未知信号及缺失子进程的语义，而不是“有序集合是否更快”。下一阶段应先加等价性回归，再实施单遍聚合，原样保留本矩阵复测；本轮到此停止。
